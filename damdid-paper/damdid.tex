\begin{abstract}
Formal neural network verification is bounded in practice by GPU memory, and it
is widely assumed that the weight matrices are what has to be distributed. We
test that assumption by porting two sharding strategies from large-scale model
training to \texttt{auto\_LiRPA}\,/\,$\alpha,\beta$-CROWN and by measuring,
rather than estimating, where the memory goes. \emph{Tensor Parallelism} shards
the weights together with the CROWN $A$-matrices, i.e.\ the specification axis:
peak memory falls by $1.97\times$ at $P{=}2$ and $3.83\times$ at $P{=}4$ and
propagation becomes $1.90\times$ and $3.49\times$ faster. Its bounds are exact
for the first sharded zone. Later zones fall back to IBP, and the bounds get
looser with each of them. \emph{Fully Sharded Data Parallelism} shards only the
weights. Its bounds are bitwise identical to the single-GPU ones, but peak
memory goes \emph{up} by 26--34\% and propagation takes up to $3.2\times$
longer, mostly in collectives. Simply staging the weights from host memory is
better on both counts. A per-node trace shows why: $A$-matrices
are $5.6\times$ the weights already at $h{=}4096$, and in
$\beta$-CROWN{+}Branch-and-Bound peak memory is linear in the number of
subdomains, $21.3 + 0.372\,B$~MB, of which weights are $0.13\%$. Sharding the
subdomain axis is therefore the direction that pays, and we quantify it: a
projected 45.0\% and 67.5\% less memory per GPU at $P{=}2$ and $P{=}4$.

\keywords{Neural network verification \and Tensor parallelism \and
Fully sharded data parallelism \and Bound propagation \and
$\alpha,\beta$-CROWN \and GPU memory.}
\end{abstract}

\section{Introduction}
\label{sec:intro}

Neural networks are now used in vehicle control, avionics and medical decision
support, where a wrong output can cause real harm. Testing is not enough there,
since each test checks a single input and not the whole set of admissible
inputs \cite{Guidotti2019Enhancing}. Formal verification proves that a property
holds for \emph{every} input in a region.

A network computes $f: \mathbb{R}^n \to \mathbb{R}^m$, and we want a property
$\psi(f(\mathbf{x}))$ to hold for every input $\mathbf{x}$ in a set
$\mathcal{X}$. Solvers search $\mathcal{X}$ for an input that breaks $\psi$.
They answer SAT with such a counterexample, or UNSAT when none exists and the
property holds \cite{marzari2025advancingneuralnetworkverification}. Most
benchmarks check local robustness. Here every $\mathbf{x}$ with
$\|\mathbf{x}-\mathbf{x}_0\|_p \leq \varepsilon$ around a sample $\mathbf{x}_0$
of class $c$ must also be classified as $c$
\cite{DBLP:journals/corr/abs-2002-03339}. Control tasks such
as ACAS~Xu use specifications over physical variables
\cite{Demarchi2023SupportingStandardization}. Networks and properties are
exchanged in ONNX and the VNN-LIB format \cite{VNNLIBWebsite}, which the VNN-COMP
competition is built on
\cite{arXiv2212VNNCOMP2022,arXiv2312VNNCOMP2023,arXiv2412VNNCOMP2024}. The
problem is NP-complete already for one hidden ReLU layer
\cite{arXiv2403RobustnessVerification}, $\exists\mathbb{R}$-complete for smooth
activations \cite{NeurIPS2021ExistsRComplete} and undecidable for some recurrent
networks \cite{IJCAI2018ReachabilityDNN}. A \emph{complete} verifier therefore
needs Branch-and-Bound, which is exponential in the worst case. An
\emph{incomplete} one uses a polynomial relaxation instead.

\subsection{The Memory Bottleneck and the Question We Ask}

In practice most verifiers use \emph{bound propagation}. The best known of
them, $\alpha,\beta$-CROWN \cite{AlphaBetaCrownVNNCOMP23}, won VNN-COMP every
year from 2021 to 2024. It runs on a GPU and computes linear bounds on the
network output. Everything it touches has to fit into the memory of one GPU.
The weights of a single hidden layer with $262\,144$ neurons and $4\,096$
inputs already take about 4~GB in float32.

Parameter sharding is the reflex borrowed from large-model training, and it
presupposes that parameters dominate. This paper implements that reflex
faithfully in a state-of-the-art verifier, measures it, and shows the
presupposition to be wrong for verification: the memory sits in the tensors
indexed by the specification and subdomain axes. That is a statement about where
multi-GPU verification research should aim.

\subsubsection{Contributions.}
\begin{enumerate}
\item Section~\ref{sec:memory} traces the memory of a CROWN pass node by node.
  For $\beta$-CROWN{+}BaB a sweep over the batch size fits
  $M_\text{peak}(B) \approx 21.3 + 0.372\,B$~MB. Weights take only $0.13\%$ of
  this peak.
\item Our TP version of \texttt{auto\_LiRPA} uses custom
  \texttt{BoundLinearTP\_Col/Row} operators
  (Sections~\ref{sec:tp},~\ref{sec:exp-tp}). With 2 GPUs peak memory is
  $1.97\times$ lower and propagation $1.90\times$ faster; with 4 GPUs the
  numbers are $3.83\times$ and $3.49\times$. We also measure how much tightness
  IBP costs in each zone and check soundness for CROWN and $\alpha$-CROWN.
\item FSDP took about 100 lines on top of \texttt{auto\_LiRPA}, and the same
  code handles convolutions and a ViT. Its bounds match the single-GPU ones bit
  for bit. The problem is memory. At $h{=}4096$ the peak is 27\% higher than on
  one GPU, and even plain host-memory staging needs less
  (Sections~\ref{sec:fsdp},~\ref{sec:exp-fsdp}).
\item We give a target for future work. All batch-dependent terms grow
  linearly with the number of subdomains, so splitting them over $P$ GPUs
  should cut memory per GPU by 45.0\% at $P{=}2$ and 67.5\% at $P{=}4$, or fit
  $P$ times more subdomains per round (Section~\ref{sec:exp-bab}).
\end{enumerate}

Our implementation, a fork of \texttt{auto\_LiRPA}\,/\,$\alpha,\beta$-CROWN,
with all experiment scripts and the collated measurement records, is publicly
available.\footnote{\url{https://github.com/vorobyov01/damdid-2026-submission}}

\section{Background}
\label{sec:verifiers}

\subsection{Bound-Propagation Methods}

\emph{IBP} \cite{CROWNPaper} propagates intervals layer by layer: for
$\mathbf{y} = W\mathbf{x} + \mathbf{b}$ it gives
$\mathbf{l}_y = W^+\mathbf{l}_x + W^-\mathbf{u}_x + \mathbf{b}$ and
$\mathbf{u}_y = W^+\mathbf{u}_x + W^-\mathbf{l}_x + \mathbf{b}$, with $W^\pm$ the
positive and negative parts of $W$. It is cheap and loses tightness fast with
depth. \emph{CROWN} \cite{CROWNPaper} instead relaxes each unstable ReLU with
pre-activation $x \in [l,u]$, $l<0<u$, by
$\lambda_l x + b_l \leq \mathrm{ReLU}(x) \leq \frac{u}{u-l}(x-l)$ and composes
the relaxations in a backward pass,
\begin{equation}
  A = \Lambda_L W_L \cdots \Lambda_1 W_1,\qquad
  \ell \;\leq\; A\mathbf{x} + \mathbf{b} \;\leq\; u,
  \label{eq:crown}
\end{equation}
with $\Lambda_i = \mathrm{diag}(\lambda_i)$. Since $A$ is linear in the original
input, cross-variable dependencies survive across all layers, which is what
makes CROWN much tighter than IBP. \emph{$\alpha$-CROWN}
\cite{AlphaBetaCrownVNNCOMP23} turns the fixed slopes into optimisable
per-neuron parameters $\alpha_i \in [0,1]$ and tightens the bound by gradient
ascent, without branching.

\emph{Complete verification} \cite{betaCROWN2021} adds Branch-and-Bound: when
the relaxation is too loose the problem is split, e.g.\ by fixing a ReLU to
$x \geq 0$ or $x < 0$, and bounds are recomputed per subdomain. $\beta$-CROWN
encodes the split constraints as Lagrangian dual variables $\beta$ inside the
propagation, so thousands of subdomains are evaluated in one batched GPU pass
with $\alpha$ and $\beta$ optimised jointly; BICCOS
\cite{NeurIPS2024BnbCuttingPlanes} strengthens the root bound with cutting
planes from the search tree, while other complete verifiers replace the search
itself, by continuous relaxation \cite{arXiv2401Marabou2}, clause learning
\cite{NeuralSATRepo}, adaptive set representations \cite{NNEnumPaper} or
mixed-integer encodings \cite{arXiv1711MIPRobustness}.

\subsection{The \texttt{auto\_LiRPA} Library}

All our work builds on \texttt{auto\_LiRPA} \cite{AutoLiRPARepo}, the library
under $\alpha,\beta$-CROWN, which expresses bound propagation over a PyTorch
computational graph and derives bounds for any intermediate node of an arbitrary
architecture. It supports \emph{batch BaB}: up to hundreds of thousands of open
subproblems are bounded in a single pass. Any modification must therefore keep
batched processing intact and stay compatible with the traced graph, which is
what makes the sharding work non-trivial.

\section{Sharding Bound Propagation}
\label{sec:method}

\subsection{Primitives, and Why Not Pipeline Parallelism}
\label{sec:primitives}

\emph{Tensor Parallelism} \cite{MegatronLM2020} splits the matrix products
inside a layer: column-parallel splits $W \in \mathbb{R}^{k \times n}$ along the
output dimension into $W^{(r)} \in \mathbb{R}^{k \times n/P}$ and each GPU
computes a partial output from a replicated input, while row-parallel splits
along the input dimension and sums the partial products, so a Column--Row pair
costs exactly one \texttt{AllReduce}. \emph{FSDP} \cite{ZeROPaper} shards every
parameter tensor across $P$ GPUs and an \texttt{AllGather} rebuilds a layer's
parameter just before it is needed, releasing it just after, so at most one full
weight is resident. \emph{Pipeline parallelism} \cite{GPipePaper} does not fit
CROWN: Equation~\ref{eq:crown} traverses \emph{all} layers in one backward pass,
so a pipeline would ship weight matrices between stages at every step, i.e.\ TP
with a worse communication pattern. TP and FSDP both run the full pass on every
GPU and differ in what they shard: TP the computation, FSDP only the storage.

\subsection{Tensor Parallelism}
\label{sec:tp}

We add two operators, \texttt{BoundLinearTP\_Col} and
\texttt{BoundLinearTP\_Row}, derived from \texttt{BoundLinear}. Each calls
\texttt{AllReduce} in \texttt{bound\_backward}. Each also has a custom ONNX
symbolic method, so JIT tracing builds the graph without running the
collective; otherwise tracing fails with \texttt{Tried to trace ProcessGroup}.
The function \texttt{tp\_shard\_bounded\_module} works on any
\texttt{BoundedModule}, including one loaded from ONNX. It replaces pairs of
consecutive \texttt{BoundLinear} nodes with their TP versions and shards the
weights. A BFS pass then marks each Column--Row subgraph as a \emph{sharded
zone}, so that its intermediate bounds are handled the same way on every rank.

TP shards $W$ and the $A$-matrices alike, so the backward step
$A \leftarrow A \cdot \Lambda_i W_i$ stays local inside a zone, and one
\texttt{AllReduce} at the Row layer restores the exact result. The ReLU between
the Column and the Row layer needs bounds on the Column outputs to pick its
slopes $\lambda_i$. Computing them by CROWN would need a separate backward pass
with communication at every step, which would give the memory back, so each
rank bounds its own Column outputs by IBP. In the first zone this costs nothing:
the Column layer is a single affine map of the input box, and IBP is exact
there. In every later zone the Column input is already an interval, and IBP
discards the correlation between its components. This is the \emph{wrapping
effect} \cite{moore2009interval}.

\paragraph{How fast tightness degrades.} Let IBP pass through
$k$ linear layers with ReLUs in between, and let $w(\cdot)$ denote
elementwise interval width. A linear layer maps widths by
$w(W\mathbf{x}) \leq |W|\,w(\mathbf{x})$ componentwise, and ReLU is
non-expansive, $w(\mathrm{ReLU}(x)) \leq w(x)$. Composing gives
\begin{equation}
  \|w_\text{out}\|_\infty \;\leq\;
  \Bigl(\textstyle\prod_{i=1}^{k}\bigl\||W_i|\bigr\|_\infty\Bigr)\,
  \|w_\text{in}\|_\infty .
  \label{eq:wrapping}
\end{equation}
This is an upper bound on \emph{IBP} widths, not a growth rate of the
CROWN--IBP gap, and it is the only claim we make: the gap is governed by the
product of layer norms, so it compounds per zone. The measured behaviour
(Table~\ref{tab:tp-correctness}) is consistent with it, and $\|\,|W|\,\|_\infty$
for the three MNIST-FC models is $19.6$, $20.4$ and $21.1$. The mechanism is
elementary: for $x_1, x_2 \in [-1,1]$ and
$W = \bigl(\begin{smallmatrix}1&1\\1&-1\end{smallmatrix}\bigr)$, CROWN gives
$y_1+y_2 = 2x_1 \in [-2,2]$ exactly, while IBP treats $y_1, y_2 \in [-2,2]$ as
independent and returns $[-4,4]$.

\subsection{Fully Sharded Data Parallelism}
\label{sec:fsdp}

\texttt{fsdp\_shard\_bounded\_module} replaces every \texttt{BoundParams}
weight with its shard along \texttt{dim=0}. For \texttt{BoundLinear} the shard
is $W^{(r)} \in \mathbb{R}^{k/P \times n}$, and for \texttt{BoundConv} it is
$W^{(r)} \in \mathbb{R}^{C_\text{out}/P \times C_\text{in} \times k_H \times k_W}$. In both layer types dimension~0 is the output axis, so
an \texttt{AllGather} along it gives back the exact matrix. A tensor stays
unsharded if its first dimension is not divisible by $P$; at $P{=}4$ this
happens only for the classifier layer. Two hooks, \texttt{fsdp\_gather\_node}
and \texttt{fsdp\_free\_node}, run inside \texttt{backward\_general} (CROWN) and
\texttt{IBP\_general} (IBP). They build the full matrix right before a layer
needs it and free it right after. The code is about 100 lines, against about
500 for TP, because it needs no new operators and leaves the graph as it is.

FSDP performs the same floating-point operations in the same order as the
single-GPU path; only the provenance of the weight tensor differs. IBP and CROWN
bounds are therefore \emph{bitwise} identical --- an exact zero, not a machine
epsilon --- which we confirm on eight configurations (MLPs of width 256 at
depths 2, 4, 6 under IBP and CROWN, and ONNX 256$\times$2 and 256$\times$4
under CROWN) at $P{=}2$ and $P{=}4$. We report it as a regression guarantee
rather than as a result, since it follows from the construction.

FSDP also composes with complete verification without extra algorithmic
machinery: each rank runs an ordinary $\beta$-CROWN{+}BaB iteration once its
weights have been gathered, and $\beta$ is managed exactly as on one GPU.
Sharding \texttt{BoundConv} over output channels required three files to change
(\texttt{fsdp\_utils.py} to admit \texttt{BoundConv} and to prevent double
sharding, \texttt{backward\_bound.py} for the gather/free in the CROWN backward,
\texttt{interval\_bound.py} for the free after IBP). Transformers needed three
JIT fixes, because \texttt{auto\_LiRPA} bakes reshape arguments in at batch
size 1 while BaB later increases the batch: \texttt{BoundReshape} substitutes
the actual batch size when $\prod(\text{new\_shape}) = x.\text{numel}()$,
\texttt{BoundConcat} takes its tensor count from the trace, and
\texttt{BoundConstantOfShape} updates its shape argument.

\section{Where the Memory Actually Is}
\label{sec:memory}

We read GPU memory from the \texttt{torch.cuda} counters and split it in two.
The \emph{resident} part $R$ is allocated before \texttt{compute\_bounds}
starts. It holds the weights, the traced graph and the inputs. The
\emph{transient} part $T = M_\text{peak} - R$ appears during the pass and holds
$A$-matrices, intermediate bounds, gathered weights and collective buffers.
Sharding can only reduce $R$.

For an MLP with $n$ inputs and $d$ hidden layers of width $h$, the weights take
$S_W = 4\,(nh + (d{-}1)h^2 + hm)$ bytes. The $A$-matrices are harder to count,
because CROWN builds a new one for every layer whose intermediate bounds it
needs. For a layer of width $h$ the specification dimension is $h$, so with $N$
inputs each $A$-tensor has shape $[N, h, h]$ and a lower/upper pair takes
$8Nh^2$ bytes. With $c$ pairs alive at the same time we get
\begin{equation}
  M_\text{peak} \;\approx\; S_W \;+\; 8\,c\,N h^2 \;+\; S_0 ,
  \label{eq:peak}
\end{equation}
where $S_0$ is the rest: graph metadata, inputs and intermediate bounds. To find
$c$ we logged the allocated memory after every node of a CROWN pass at
$h{=}4096$, $d{=}4$, $N{=}1$. It went from $417$ to $1844$~MB, and most of the
increments were exactly $128$~MB, the size of one $A$-pair of shape
$[4096,1,4096]$. When the pass finished, $18$ such tensors were still alive.
That gives $c{=}9$ and $1152$~MB of $A$-matrices next to $204.5$~MB of weights.
With more inputs or a wider output specification the $A$-matrices grow further,
while the weights stay the same.

Equation~\ref{eq:peak} gives a ceiling for FSDP. Sharding turns $S_W$ into
$S_W/P$ and does not touch the other terms, so no implementation can save more
than
\begin{equation}
  \eta_\text{max} \;=\; \Bigl(1 - \tfrac{1}{P}\Bigr)\,
  \frac{S_W}{M_\text{peak}} .
  \label{eq:ceiling}
\end{equation}
For our MLPs $\eta_\text{max}$ is $5.3\%$ at $h{=}4096$, $d{=}4$ and $5.2\%$ at
$h{=}8192$. It drops to $2.9\%$ at $d{=}8$ and rises to $7.9\%$ at $P{=}4$. A
real implementation also pays for the gathered weight and the NCCL buffers, and
Section~\ref{sec:exp-fsdp} shows that these costs are larger than the saving.

\paragraph{In complete verification the axis is the subdomain count.}
In $\beta$-CROWN{+}BaB the largest tensors are indexed by the number $B$ of
subdomains in the batch. This holds for the per-neuron $\alpha$ slopes, whose
shape is $(\text{layers}) \times (\text{specs}) \times (B) \times
(\text{neurons})$, and also for the intermediate bounds and the $A$-matrices.
The weights do not depend on $B$. We swept $B$ from 128 to 4096 on
\texttt{mnist-net\_256x6} (Table~\ref{tab:bab-breakdown}) and fitted a line
through the six points:
\begin{equation}
  M_\text{peak}(B) \;\approx\; 21.3 + 0.372\,B \quad\text{MB},
  \label{eq:bab-law}
\end{equation}
Each batch-dependent term doubles when $B$ doubles, while the weights stay at
$2.03$~MB, which is $0.13\%$ of the peak at $B{=}4096$. One might expect the
$\alpha$ tensors to dominate, but at $B{=}4096$ they take only $121$~MB ($7.9\%$
of the peak). Intermediate bounds and $A$-matrices take $290$~MB each
($18.8\%$). We could not attribute the remaining ${\approx}54\%$ to a tensor
class, but it also grows linearly with $B$, so the axis worth sharding is $B$.

\section{Experiments}
\label{sec:experiments}

\paragraph{Setup.}
Unless stated otherwise, runs used 4$\times$~NVIDIA RTX~PRO~4000 Blackwell
(24~GB, PCIe, no NVLink, driver 580.159.04), 48 vCPU, PyTorch 2.8.0+cu128,
CUDA 12.8 and NCCL with
\texttt{NCCL\_P2P\_DISABLE=1}, launched by \texttt{torchrun}, with seed 42, one
discarded warm-up and three measured repeats. Each mode runs in its own process.
Under FSDP the returned bound tensors keep an autograd graph alive, and in a
shared process this memory would be counted in the peak of the next
measurement. The ViT and
CIFAR-100 checks of Section~\ref{sec:exp-arch} ran on 2$\times$~NVIDIA A40
(48~GB). We also measured the MLP configurations on the A40, and the peaks agree
to four significant digits, since allocated memory depends only on tensor
shapes.

\subsection{FSDP: Exactness, and Its Limits}

On eight configurations (MLPs of width 256 at depths 2, 4, 6 under IBP and
CROWN; ONNX 256$\times$2 and 256$\times$4 under CROWN) FSDP reproduces the
single-GPU bounds with $|\Delta lb| = |\Delta ub| = 0.00$, an exact zero, at
both $P{=}2$ and $P{=}4$. One qualification is due. In the \emph{optimised}
$\alpha$/$\beta$ path a distributed
run does not match a plain single-GPU run bit for bit: on
\texttt{mnist-net\_256x6} at $\varepsilon{=}0.05$, three of nine specification
bounds differ, by at most $6.10\times10^{-5}$ absolute and
$1.17\times10^{-7}$ relative. Sharding is not the cause. Our distributed
launcher disables the TorchScript fusers, a workaround for a strides assertion
that fires only on non-primary GPUs, and reproducing exactly that fuser
configuration on a single GPU with no process group at all reproduces the
distributed bounds digit for digit, while the untouched single-GPU run keeps its
own values. The deviation is the price of the fuser workaround, not of weight
sharding, so FSDP is exact in the sense we claimed --- but a distributed run of
$\alpha,\beta$-CROWN is not bit-identical to a single-GPU one for reasons that
have nothing to do with sharding, and that is worth knowing for anyone
comparing multi-GPU verification results.

The weight shards are exactly $1/P$ of the weights
(Table~\ref{tab:fsdp-memory}), but peak memory rises by $26$--$34\%$, and the
ceiling of Equation~\ref{eq:ceiling} explains why: at
$h{=}4096$, $d{=}4$ the whole weight term is $10.5\%$ of the peak, so
$P{=}2$ could have saved at most $5.3\%$ of it, less than the cost of staging a
full weight. Going from $P{=}2$ to $P{=}4$ moves the peak by $0.1$~MB out of
$2\,476$ while adding $50$~ms of collectives. These numbers come from our FSDP
code after two fixes. One removed a second full copy of the weight that every
gather allocated, which lowered the peak by about $2\%$. The other made the
gathered weights free after the pass. A shard, however, is still a view of the
full weight tensor, so the full storage stays allocated.
Releasing it would lower each FSDP peak by $(1-1/P)\,S_W$, which is less than
the gap to the single-GPU peak in every row of Table~\ref{tab:fsdp-memory}.

Propagation is $2.3$--$3.2\times$ slower under FSDP=2 at $h \geq 4096$
($1.3\times$ at $h{=}1024$, the smallest workload), and $57$--$70\%$ of the
wall-clock is spent inside \texttt{AllGather}: $166.7$ of $236.6$~ms at
$h{=}4096$, $583.5$ of $983.3$~ms at $h{=}8192$. On a PCIe machine without
NVLink that overhead is structural, since one full weight per layer crosses the
bus at every intermediate-bound computation --- 19 collectives and $842$~MB
moved for a $d{=}4$ pass at $h{=}4096$.

\paragraph{The naive baseline is better.} A simpler alternative to sharding is
to keep the weights in host memory and stage them per layer. We
implemented this baseline by reusing the same hook sites with a host-to-device
copy in place of the collective, which leaves \emph{no} weight bytes resident on
the GPU --- a strictly larger reduction than FSDP's $1/P$ --- and produces bounds
identical to the single-GPU reference. It wins on both axes: at $h{=}4096$,
$d{=}4$ it needs $2\,271.6$~MB against FSDP's $2\,476.0$ and $103.3$~ms against
$236.6$, and the pattern holds at every size (Tables~\ref{tab:fsdp-memory},
\ref{tab:fsdp-time}). Activation checkpointing, the other naive alternative, does
not apply at all: the CROWN backward stores no forward activations to recompute,
and its $A$-matrices are live because they are still needed.

That the crude mechanism beats the sophisticated one is the clearest statement of
this paper's finding. Neither mechanism can win, because both pay to stage a full
weight into a pass whose peak is set by tensors they never touch: at $h{=}4096$
the staged copies that \texttt{auto\_LiRPA} retains past the layer that needs
them cost $531$~MB, more than twice the $204.5$~MB of weights either mechanism
removes.

Two things follow. First, FSDP cannot help here and does not: at $B{=}512$ the
peak is $211.9$~MB on one GPU and $214.9$~MB per rank at both $P{=}2$ and
$P{=}4$, because there are $2.03$~MB of weights to shard and the
\texttt{AllGather} buffers cost more than that.

Second, Equation~\ref{eq:bab-law} makes the pay-off of sharding the subdomain
axis calculable instead of speculative. Splitting a global batch $B$ across $P$
GPUs leaves each with $B/P$ subdomains and hence
$21.3 + 0.372\,B/P$~MB, i.e.\ $45.0\%$ less memory per GPU at $P{=}2$ and
$67.5\%$ less at $P{=}4$ for $B{=}512$ ($49.3\%$ and $73.9\%$ at
$B{=}4096$). The per-GPU workload of the split is a single-GPU run at $B/P$,
which Table~\ref{tab:bab-breakdown} measures directly; what the projection
leaves out is the cost of gathering the per-rank results. Since $B$ is a tunable
parameter, the law also reads the other way: at the same memory per GPU, $P$
GPUs bound $P$ times more subdomains per round. This throughput gain is the
practical pay-off.

Our implementation of the split is partial. If the domains are scattered before
\texttt{build\_history\_and\_set\_bounds}, each rank builds its own state and
propagates its own chunk correctly. Domain parallelism does not compose with
FSDP: once ranks hold different subdomains, their per-layer \texttt{AllGather}
sequences diverge and NCCL deadlocks. We therefore disable weight sharding in
this mode, which costs nothing here, the weights being $2.03$~MB. The gather of
the per-rank results still stalls, so we report the projection rather than a
measurement.

\subsection{Convolutions and Transformers: Correctness Checks}
\label{sec:exp-arch}

These runs show that the sharding code also works beyond MLPs. We treat them as
correctness checks only, since memory changes by at most 3\% in either
direction. On the
VNN-COMP'23 ViT \texttt{pgd\_2\_3\_16} (2 blocks, 3 heads, $0.3$~MB of weights)
\cite{arXiv2312VNNCOMP2023}, after the three JIT fixes of
Section~\ref{sec:fsdp}, FSDP=2 completes 78 BaB domains over 10 rounds at
$1\,020.1$~MB per rank with $|\Delta lb| = 0.00$ at printed precision --- to our
knowledge the first Transformer run through BaB in $\alpha,\beta$-CROWN with
sharded weights. On CIFAR-100 ResNets \cite{arXiv2412VNNCOMP2024} with
\texttt{BoundConv} sharding (batch 64, \texttt{max\_iterations} 5), ResNet-med
runs 130 domains over 5 rounds at $930$~MB per rank against $960$~MB on one GPU
and exhausts its budget (\emph{unknown}), while ResNet-large (${\approx}95$~MB
of weights) is proved \textbf{unsat} by $\alpha$-CROWN at initialisation at
$4\,641.5$~MB per rank against $4\,610.6$~MB on one GPU. That \emph{unsat} is a
correctness check, not a benefit: no BaB ran, and the FSDP peak is the higher of
the two, its \texttt{AllGather} overhead exceeding what sharding $95$~MB of
weights returns when the $\alpha$ tensors alone exceed 4~GB.

\section{Related Work}
\label{sec:related}

\paragraph{Bound propagation.} CROWN \cite{CROWNPaper} introduced the backward
linear relaxation, $\alpha$-CROWN \cite{AlphaBetaCrownVNNCOMP23} and
$\beta$-CROWN \cite{betaCROWN2021} added optimisable slopes and dual encoding of
branching constraints, DeepPoly \cite{DeepPolyAbstractDomain} works in a
polyhedral abstract domain and OSIP \cite{arXiv2212OSIP} optimises symbolic
interval propagation.

\paragraph{Parallel and multi-GPU verification.} Earlier parallel verifiers
follow two lines, and neither deals with the memory of the parameters. The
first splits the search space. Marabou's Split-and-Conquer
\cite{Wu2020Parallelization} partitions the input domain across CPU workers
with iterative deepening, and $\beta$-CROWN \cite{betaCROWN2021} batches
subdomains on one GPU. The second moves a fixed abstract domain to the GPU, as
GPUPoly \cite{ScalingPolyhedralGPU} does for DeepPoly. Both scale the
\emph{number} of subproblems, while we looked at the memory of one. Our
measurements show that this memory sits in the subproblem batch, so splitting
domains and saving memory turn out to be the same problem.

\paragraph{Sharding for training.} Megatron-LM \cite{MegatronLM2020} introduced
intra-layer tensor parallelism, ZeRO \cite{ZeROPaper} shards parameters,
gradients and optimiser states, and GPipe \cite{GPipePaper} pipelines layer
groups with micro-batches. To our knowledge neither had been applied to
bound-propagation verification, which is what makes the negative result worth
recording: a training step is dominated by parameters and optimiser state, a
verification pass by tensors indexed by specifications and subdomains.

\section{Conclusion}
\label{sec:conclusion}

Both sharding schemes were easy to add to $\alpha,\beta$-CROWN, but they
behave very differently. TP shards the specification axis, so peak memory drops
by $1.97\times$ on 2 GPUs and $3.83\times$ on 4, and propagation gets
$1.90\times$ and $3.49\times$ faster. Its bounds stay exact in the first
sharded zone and loosen in later ones, where IBP is used. FSDP keeps IBP and
CROWN bounds bitwise identical, yet it adds 26--34\% to peak memory and up to
$3.2\times$ to propagation time, and staging weights from host memory does
better on both. The weights are only $6$--$11\%$ of the peak, so
sharding half of them can save a few percent at most.

The finding we would carry forward is the measurement, not either
mechanism. In incomplete verification $A$-matrices exceed weights by
$5.6\times$ at $h{=}4096$; in complete verification peak memory is
$21.3 + 0.372\,B$~MB in the number of subdomains, of which weights are
$0.13\%$. Multi-GPU verification should therefore shard the subdomain axis, for
which we project $45.0\%$ and $67.5\%$ less memory per GPU at $P{=}2,4$, or $P$
times more subdomains per round at the same memory. The scatter already runs
correctly per rank; the remaining task is the gather of per-rank results.
Sharding the specification
axis without the IBP fallback --- exact intermediate bounds inside later sharded
zones --- is the harder and more valuable open problem.
