\begin{abstract}
GPU memory limits the size of networks that formal verification can handle, and
the usual assumption is that the weight matrices are what has to be split across
GPUs. We tested this assumption in \texttt{auto\_LiRPA}\,/\,$\alpha,\beta$-CROWN.
We added two sharding methods from large-model training and measured where the
memory actually goes. \emph{Tensor Parallelism} (TP) splits the weights together
with the CROWN $A$-matrices. On 2 GPUs it lowered peak memory by $1.97\times$ and
made propagation $1.90\times$ faster; on 4 GPUs the factors were $3.83\times$ and
$3.49\times$. Its bounds are exact in the first sharded zone and get looser in
later zones, which use IBP. \emph{Fully Sharded Data Parallelism} (FSDP) splits
only the weights. Its bounds match the single-GPU bounds bit for bit, but peak
memory grew by 26--34\% and propagation took up to $3.2\times$ longer. Copying
the weights from host memory one layer at a time needed less memory and less
time than FSDP. A per-node memory trace explains this. At $h{=}4096$ the
$A$-matrices take $5.6$ times more memory than the weights. In $\beta$-CROWN with
Branch-and-Bound the peak grows linearly with the number of subdomains $B$, as
$21.3 + 0.372\,B$~MB, and weights are $0.13\%$ of it. We therefore expect more
from splitting the subdomains across GPUs, and estimate 45.0\% less memory per
GPU at $P{=}2$ and 67.5\% at $P{=}4$.

\keywords{Neural network verification \and Tensor parallelism \and
Fully sharded data parallelism \and Bound propagation \and
$\alpha,\beta$-CROWN \and GPU memory.}
\end{abstract}

\section{Introduction}
\label{sec:intro}

Neural networks are used in vehicle control and in medical decision support,
where a wrong output can cause real harm. Testing checks one input at a time
and cannot rule out a bad input that nobody tried \cite{Guidotti2019Enhancing}.
Formal verification proves that a property holds for \emph{every} input in a
region.

We use the standard setting. A network is a function
$f: \mathbb{R}^n \to \mathbb{R}^m$, a specification is a property
$\psi(f(\mathbf{x}))$ that should hold on an input set $\mathcal{X}$, and a
solver searches $\mathcal{X}$ for an input that violates $\psi$. When it finds
one, the answer is SAT and the input is a counterexample; when it proves that
none exists, the answer is UNSAT
\cite{marzari2025advancingneuralnetworkverification}. By far the most common
specification is local robustness, where every $\mathbf{x}$ within
$\varepsilon$ of a sample $\mathbf{x}_0$ of class $c$, in some $p$-norm, has to
be classified as $c$ as well \cite{DBLP:journals/corr/abs-2002-03339}. Control
benchmarks such as ACAS~Xu state their properties over physical variables
instead \cite{Demarchi2023SupportingStandardization}. Both networks and
specifications are exchanged as ONNX and VNN-LIB files \cite{VNNLIBWebsite},
the formats of the VNN-COMP competition
\cite{arXiv2212VNNCOMP2022,arXiv2312VNNCOMP2023,arXiv2412VNNCOMP2024}. None of
this is easy to decide. Verification is NP-complete already with one hidden
ReLU layer \cite{arXiv2403RobustnessVerification}, $\exists\mathbb{R}$-complete
for smooth activations \cite{NeurIPS2021ExistsRComplete} and undecidable for
some recurrent models \cite{IJCAI2018ReachabilityDNN}, so \emph{complete}
verifiers rely on Branch-and-Bound, with exponential worst-case time, while
\emph{incomplete} verifiers settle for a polynomial relaxation and may answer
\emph{unknown}.

\subsection{The Memory Bottleneck and the Question We Ask}

In practice most verifiers use \emph{bound propagation}. The best known of
them, $\alpha,\beta$-CROWN \cite{AlphaBetaCrownVNNCOMP23}, won VNN-COMP every
year from 2021 to 2024. It computes linear bounds on the network output on a
GPU, and everything it touches has to fit into that GPU's memory. The weights
of a single hidden layer with $262\,144$ neurons and $4\,096$ inputs already
take about 4~GB in float32.

The obvious remedy is to shard the parameters across GPUs, as the training of
large models does. This assumes that the parameters are what fills the memory.
We implemented two such sharding methods in a state-of-the-art verifier and
measured them, and the assumption turned out to be wrong. In verification the
memory goes to the tensors indexed by the specification and by the subdomains,
and this is where multi-GPU verification needs to aim.

\subsubsection{Contributions.}
\begin{enumerate}
\item A node-by-node memory trace of a CROWN pass (Section~\ref{sec:memory}).
  For $\beta$-CROWN{+}BaB a sweep over the batch size gives
  $M_\text{peak}(B) \approx 21.3 + 0.372\,B$~MB, and the weights are $0.13\%$
  of this peak.
\item A TP version of \texttt{auto\_LiRPA} built on two new operators,
  \texttt{BoundLinearTP\_Col/Row} (Sections~\ref{sec:tp},~\ref{sec:exp-tp}).
  Peak memory drops $1.97\times$ on 2 GPUs and $3.83\times$ on 4, and
  propagation gets $1.90\times$ and $3.49\times$ faster. We also measure the
  tightness lost to IBP in each zone and check soundness for CROWN and
  $\alpha$-CROWN.
\item An FSDP version in about 100 lines, which also handles convolutions and a
  ViT (Sections~\ref{sec:fsdp},~\ref{sec:exp-fsdp}). Its bounds match the
  single-GPU ones bit for bit, but at $h{=}4096$ its peak is 27\% higher than
  on one GPU. Even copying the weights from host memory needs less.
\item A target for future work (Section~\ref{sec:exp-bab}). Every
  batch-dependent term grows linearly with the number of subdomains, so
  splitting them over $P$ GPUs should cut memory per GPU by 45.0\% at $P{=}2$
  and 67.5\% at $P{=}4$, or fit $P$ times more subdomains per round.
\end{enumerate}

The code, a fork of \texttt{auto\_LiRPA}\,/\,$\alpha,\beta$-CROWN, is public
together with the experiment scripts and the raw
measurements.\footnote{\url{https://github.com/vorobyov01/damdid-2026-submission}}

\section{Background}
\label{sec:verifiers}

\subsection{Bound-Propagation Methods}

\emph{IBP} \cite{CROWNPaper} propagates intervals layer by layer. For
$\mathbf{y} = W\mathbf{x} + \mathbf{b}$ it gives
$\mathbf{l}_y = W^+\mathbf{l}_x + W^-\mathbf{u}_x + \mathbf{b}$ and
$\mathbf{u}_y = W^+\mathbf{u}_x + W^-\mathbf{l}_x + \mathbf{b}$, where $W^\pm$
are the positive and negative parts of $W$. IBP is cheap, but its intervals
widen quickly with depth. \emph{CROWN} \cite{CROWNPaper} keeps more
information. It relaxes each unstable ReLU, with pre-activation $x \in [l,u]$,
$l<0<u$, by $\lambda_l x + b_l \leq \mathrm{ReLU}(x) \leq \frac{u}{u-l}(x-l)$
and composes these relaxations in a backward pass,
\begin{equation}
  A = \Lambda_L W_L \cdots \Lambda_1 W_1,\qquad
  \ell \;\leq\; A\mathbf{x} + \mathbf{b} \;\leq\; u,
  \label{eq:crown}
\end{equation}
with $\Lambda_i = \mathrm{diag}(\lambda_i)$. The matrix $A$ is linear in the
original input, so dependencies between variables survive through all layers.
This is why CROWN is much tighter than IBP. \emph{$\alpha$-CROWN}
\cite{AlphaBetaCrownVNNCOMP23} makes the slopes free parameters
$\alpha_i \in [0,1]$, one per neuron, and optimizes them by gradient ascent,
still without branching.

\emph{Complete verification} \cite{betaCROWN2021} adds Branch-and-Bound on top
of this. When the relaxation is too loose, the problem is split, for example by
fixing one ReLU to $x \geq 0$ or to $x < 0$, and the bounds are recomputed on
each subdomain. $\beta$-CROWN folds the split constraints into the propagation
as Lagrangian dual variables $\beta$, so thousands of subdomains can be bounded
in one batched GPU pass, with $\alpha$ and $\beta$ optimized together. BICCOS
\cite{NeurIPS2024BnbCuttingPlanes} adds cutting planes from the search tree to
strengthen the root bound. Other complete verifiers organize the search
differently, through continuous relaxation \cite{arXiv2401Marabou2}, clause
learning \cite{NeuralSATRepo}, adaptive set representations \cite{NNEnumPaper}
or mixed-integer encodings \cite{arXiv1711MIPRobustness}.

\subsection{The \texttt{auto\_LiRPA} Library}

All our work builds on \texttt{auto\_LiRPA} \cite{AutoLiRPARepo}, the library
behind $\alpha,\beta$-CROWN. It runs bound propagation over a traced PyTorch
graph and can bound any intermediate node of an arbitrary architecture. It also
supports \emph{batched BaB}, where up to hundreds of thousands of open
subproblems are bounded in one pass. Our changes had to keep both the batching
and the traced graph intact, and most of the effort in sharding went into that.

\section{Sharding Bound Propagation}
\label{sec:method}

\subsection{Primitives, and Why Not Pipeline Parallelism}
\label{sec:primitives}

\emph{Tensor Parallelism} \cite{MegatronLM2020} splits the matrix product
inside a layer. In a column-parallel layer every GPU holds a slice
$W^{(r)} \in \mathbb{R}^{k/P \times n}$ of the weight $W \in \mathbb{R}^{k \times n}$,
cut along the output dimension, and computes its part of the output from the
full input. In a row-parallel layer the cut goes along the input dimension, each
GPU multiplies its slice of the input, and the partial products are summed. A
Column--Row pair therefore needs one \texttt{AllReduce}. \emph{FSDP}
\cite{ZeROPaper} does not split the computation at all. Each parameter tensor
is stored in $P$ pieces, one per GPU. Right before a layer runs, an
\texttt{AllGather} rebuilds the full weight, and the copy is dropped right
after, so at most one full weight sits on a GPU at a time. We did not try
\emph{pipeline parallelism} \cite{GPipePaper}. The CROWN backward pass in
Equation~\ref{eq:crown} runs through all layers, and a pipeline would have to
ship weight matrices between stages at every step, which is TP with more
communication. Both TP and FSDP run the whole pass on every GPU. The difference
is that TP splits the arithmetic and FSDP splits only where the weights are
stored.

\subsection{Tensor Parallelism}
\label{sec:tp}

We added two operators, \texttt{BoundLinearTP\_Col} and
\texttt{BoundLinearTP\_Row}, as subclasses of \texttt{BoundLinear}. Their
\texttt{bound\_backward} calls \texttt{AllReduce}. JIT tracing must not run the
collective, since it then fails with \texttt{Tried to trace ProcessGroup}, so
both operators also register a custom ONNX symbolic method. The function
\texttt{tp\_shard\_bounded\_module} takes any \texttt{BoundedModule}, including
one loaded from ONNX, swaps pairs of consecutive \texttt{BoundLinear} nodes for
their TP versions and shards the weights. A BFS pass then marks each Column--Row
subgraph as a \emph{sharded zone}, so that every rank handles its intermediate
bounds in the same way.

Since TP shards both $W$ and the $A$-matrices, the backward step
$A \leftarrow A \cdot \Lambda_i W_i$ is local inside a zone, and one
\texttt{AllReduce} at the Row layer gives the exact result. The difficulty is the
ReLU between the Column and the Row layer. To choose its slopes $\lambda_i$,
CROWN needs bounds on the Column outputs. Computing them with CROWN would take
another backward pass with communication at every step and would cost the memory
we just saved. Each rank therefore bounds its own Column outputs with IBP. For
the first zone this changes nothing, because the Column layer is one affine map
of the input box and IBP gives the exact interval there. In later zones the
input of the Column layer is already an interval, and IBP loses the correlation
between its components. This is known as the \emph{wrapping effect}
\cite{moore2009interval}.

\paragraph{How fast tightness degrades.} Suppose IBP passes through $k$
linear layers with ReLUs between them, and write $w(\cdot)$ for the elementwise
width of an interval. A linear layer satisfies
$w(W\mathbf{x}) \leq |W|\,w(\mathbf{x})$ componentwise, and a ReLU never widens
an interval, $w(\mathrm{ReLU}(x)) \leq w(x)$. Chaining the layers gives
\begin{equation}
  \|w_\text{out}\|_\infty \;\leq\;
  \Bigl(\textstyle\prod_{i=1}^{k}\bigl\||W_i|\bigr\|_\infty\Bigr)\,
  \|w_\text{in}\|_\infty .
  \label{eq:wrapping}
\end{equation}
We use the inequality only as a guide. It bounds the IBP widths from above and
says nothing precise about the gap between CROWN and IBP, but it shows that the
gap grows with the product of the layer norms, one factor per zone, and
Table~\ref{tab:tp-correctness} behaves that way. For the three MNIST-FC models
$\|\,|W|\,\|_\infty$ is $19.6$, $20.4$ and $21.1$. In two variables the loss is
easy to see. Take $x_1, x_2 \in [-1,1]$ and
$W = \bigl(\begin{smallmatrix}1&1\\1&-1\end{smallmatrix}\bigr)$. CROWN knows
that $y_1+y_2 = 2x_1 \in [-2,2]$; IBP treats $y_1$ and $y_2$ as independent
intervals $[-2,2]$ and returns $[-4,4]$.

\subsection{Fully Sharded Data Parallelism}
\label{sec:fsdp}

\texttt{fsdp\_shard\_bounded\_module} keeps on each GPU only its part of every
\texttt{BoundParams} weight, cut along \texttt{dim=0}. A \texttt{BoundLinear}
weight becomes $W^{(r)} \in \mathbb{R}^{k/P \times n}$, and a \texttt{BoundConv}
weight becomes
$W^{(r)} \in \mathbb{R}^{C_\text{out}/P \times C_\text{in} \times k_H \times k_W}$.
Dimension~0 is the output axis in both cases, so an \texttt{AllGather} along it
restores the exact matrix. If the first dimension is not divisible by $P$, we
leave the tensor whole. At $P{=}4$ this happens only for the classifier. The
hooks \texttt{fsdp\_gather\_node} and \texttt{fsdp\_free\_node} sit in
\texttt{backward\_general} (CROWN) and \texttt{IBP\_general} (IBP). They gather a
weight right before its layer runs and free it right after. The whole change is
about 100 lines of code, against about 500 for TP, which needed new operators
and changes to the graph.

FSDP does the same floating-point operations in the same order as the
single-GPU code. Only the origin of the weight tensor differs, so IBP and CROWN
bounds are \emph{bitwise} identical. Section~\ref{sec:exp-fsdp-exact} confirms
this, and we use it as a regression test.

Complete verification needs no change to the algorithm. Once its weights are
gathered, each rank runs an ordinary $\beta$-CROWN{+}BaB iteration, and the
$\beta$ variables are handled exactly as on one GPU. Convolutions required small
changes in three files, so that \texttt{fsdp\_utils.py} accepts
\texttt{BoundConv} and never shards a weight twice,
\texttt{backward\_bound.py} gathers and frees the conv weights in the CROWN
backward, and \texttt{interval\_bound.py} frees them after IBP. Transformers
were harder. During tracing \texttt{auto\_LiRPA} bakes the reshape arguments in
at batch size 1, while BaB later runs larger batches. We patched three
operators. \texttt{BoundReshape} inserts the actual batch size whenever
$\prod(\text{new\_shape}) = x.\text{numel}()$, \texttt{BoundConcat} reads its
tensor count from the trace, and \texttt{BoundConstantOfShape} updates its
shape argument.

\section{Where the Memory Actually Is}
\label{sec:memory}

We read GPU memory from the \texttt{torch.cuda} counters and split it in two.
The \emph{resident} part $R$ is allocated before \texttt{compute\_bounds}
starts. It holds the weights, the traced graph and the inputs. The
\emph{transient} part $T = M_\text{peak} - R$ appears during the pass and holds
$A$-matrices, intermediate bounds, gathered weights and collective buffers.
Sharding can only reduce $R$.

For an MLP with $n$ inputs and $d$ hidden layers of width $h$, the weights take
$S_W = 4\,(nh + (d{-}1)h^2 + hm)$ bytes. The $A$-matrices are harder to count,
because CROWN builds a new one for every layer whose intermediate bounds it
needs. For a layer of width $h$ the specification dimension is $h$, so with $N$
inputs each $A$-tensor has shape $[N, h, h]$ and a lower/upper pair takes
$8Nh^2$ bytes. With $c$ pairs alive at the same time we get
\begin{equation}
  M_\text{peak} \;\approx\; S_W \;+\; 8\,c\,N h^2 \;+\; S_0 ,
  \label{eq:peak}
\end{equation}
where $S_0$ is the rest: graph metadata, inputs and intermediate bounds. To find
$c$ we logged the allocated memory after every node of a CROWN pass at
$h{=}4096$, $d{=}4$, $N{=}1$. It went from $417$ to $1844$~MB, and most of the
increments were exactly $128$~MB, the size of one $A$-pair of shape
$[4096,1,4096]$. When the pass finished, $18$ such tensors were still alive.
That gives $c{=}9$ and $1152$~MB of $A$-matrices next to $204.5$~MB of weights.
With more inputs or a wider output specification the $A$-matrices grow further,
while the weights stay the same.

Equation~\ref{eq:peak} also puts a ceiling on what FSDP can save. Sharding
replaces $S_W$ by $S_W/P$ and leaves the other terms alone, so no implementation
can save more than
\begin{equation}
  \eta_\text{max} \;=\; \Bigl(1 - \tfrac{1}{P}\Bigr)\,
  \frac{S_W}{M_\text{peak}} .
  \label{eq:ceiling}
\end{equation}
For our MLPs $\eta_\text{max}$ is $5.3\%$ at $h{=}4096$, $d{=}4$ and $5.2\%$ at
$h{=}8192$; it drops to $2.9\%$ at $d{=}8$ and rises to $7.9\%$ at $P{=}4$. A
real implementation also has to pay for the gathered weight and for the NCCL
buffers. Section~\ref{sec:exp-fsdp} shows that these cost more than the ceiling
allows to save.

\paragraph{In complete verification the axis is the subdomain count.}
In $\beta$-CROWN{+}BaB the largest tensors are indexed by the number $B$ of
subdomains in the batch. This holds for the per-neuron $\alpha$ slopes, whose
shape is $(\text{layers}) \times (\text{specs}) \times (B) \times
(\text{neurons})$, and also for the intermediate bounds and the $A$-matrices.
The weights do not depend on $B$. We swept $B$ from 128 to 4096 on
\texttt{mnist-net\_256x6} (Table~\ref{tab:bab-breakdown}) and fitted a line
through the six points:
\begin{equation}
  M_\text{peak}(B) \;\approx\; 21.3 + 0.372\,B \quad\text{MB}.
  \label{eq:bab-law}
\end{equation}
Each batch-dependent term doubles when $B$ doubles, while the weights stay at
$2.03$~MB, which is $0.13\%$ of the peak at $B{=}4096$. One might expect the
$\alpha$ tensors to dominate, but at $B{=}4096$ they take only $121$~MB ($7.9\%$
of the peak). Intermediate bounds and $A$-matrices take $290$~MB each
($18.8\%$). We could not attribute the remaining ${\approx}54\%$ to a tensor
class, but it also grows linearly with $B$, so the axis worth sharding is $B$.

\section{Experiments}
\label{sec:experiments}

\paragraph{Setup.}
Unless stated otherwise, runs used 4$\times$~NVIDIA RTX~PRO~4000 Blackwell
(24~GB, PCIe, no NVLink, driver 580.159.04), 48 vCPU, PyTorch 2.8.0+cu128,
CUDA 12.8 and NCCL with
\texttt{NCCL\_P2P\_DISABLE=1}, launched by \texttt{torchrun}, with seed 42, one
discarded warm-up and three measured repeats. Each mode runs in its own process.
Under FSDP the returned bound tensors keep an autograd graph alive, and in a
shared process this memory would be counted in the peak of the next

(48~GB). We also measured the MLP configurations on the A40, and the peaks agree
to four significant digits, since allocated memory depends only on tensor
shapes.

\subsection{FSDP: Exactness, and Its Limits}
\label{sec:exp-fsdp-exact}

We checked FSDP on eight configurations: MLPs of width 256 at depths 2, 4 and 6
under IBP and CROWN, and the ONNX models 256$\times$2 and 256$\times$4 under
CROWN. In all of them, at both $P{=}2$ and $P{=}4$, FSDP reproduces the
single-GPU bounds with $|\Delta lb| = |\Delta ub| = 0.00$, an exact zero. There
is one caveat. In the \emph{optimized} $\alpha$/$\beta$ path, a distributed run
does not match a plain single-GPU run bit for bit. On
\texttt{mnist-net\_256x6} at $\varepsilon{=}0.05$, three of nine specification
bounds differ, by at most $6.10\times10^{-5}$ absolute and $1.17\times10^{-7}$
relative. Sharding is not the cause. Our distributed launcher turns off the
TorchScript fusers to avoid a strides assertion that fires only on non-primary
GPUs. With the same fuser settings, a single GPU without any process group
gives exactly the distributed bounds, while the default single-GPU run keeps
its own values. FSDP itself is therefore exact. The small differences come from
the fuser workaround, and anyone comparing multi-GPU runs of
$\alpha,\beta$-CROWN with single-GPU runs should expect them.

Table~\ref{tab:fsdp-memory} shows the weight shards at exactly $1/P$ of the
weights and, at the same time, a peak memory $26$--$34\%$ above the single-GPU
run. Equation~\ref{eq:ceiling} explains the second number. At $h{=}4096$,
$d{=}4$ the weights are $10.5\%$ of the peak, so $P{=}2$ could have saved at
most $5.3\%$, and staging one full weight costs more than that. Going from
$P{=}2$ to $P{=}4$ changes the peak by $0.1$~MB out of $2\,476$ and adds
$50$~ms of collectives. These numbers come from our FSDP code after two fixes.
One removed a second full copy of the weight that every gather allocated, which
lowered the peak by about $2\%$. The other frees the gathered weights after the
pass. A shard, however, is still a view of the full weight tensor, so the full
storage stays allocated. Releasing it would lower each FSDP peak by
$(1-1/P)\,S_W$, and in every row of Table~\ref{tab:fsdp-memory} that is less
than the gap to the single-GPU peak.

Propagation is $2.3$--$3.2\times$ slower under FSDP=2 at $h \geq 4096$
($1.3\times$ at $h{=}1024$, the smallest workload), and $57$--$70\%$ of the
wall-clock is spent inside \texttt{AllGather}: $166.7$ of $236.6$~ms at
$h{=}4096$, $583.5$ of $983.3$~ms at $h{=}8192$. On a PCIe machine without
NVLink this overhead cannot be avoided, because one full weight per layer
crosses the bus at every intermediate-bound computation. A $d{=}4$ pass at
$h{=}4096$ runs 19 collectives and moves $842$~MB.

\paragraph{The naive baseline is better.} A simpler way to get the weights off
the GPU is to keep them in host memory and copy each one over when its layer
runs. We built this baseline on the same hooks, with a host-to-device copy in
place of the collective. It leaves no weight bytes on the GPU at all, so it
removes more than the $(1-1/P)$ that FSDP can, and its bounds equal the
single-GPU reference. It also wins on time. At $h{=}4096$, $d{=}4$ it needs
$2\,271.6$~MB and $103.3$~ms, against $2\,476.0$~MB and $236.6$~ms for FSDP,
and the picture is the same at every size (Tables~\ref{tab:fsdp-memory}
and~\ref{tab:fsdp-time}). Activation checkpointing, the other standard trick,
does not apply. The CROWN backward has no forward activations to recompute, and
its $A$-matrices are live because later steps still need them.

Neither the baseline nor FSDP gets below the single-GPU peak, and the reason is
the same for both. Each brings a full weight into a pass whose peak is set by
tensors it never touches. At $h{=}4096$ the copies that \texttt{auto\_LiRPA}
keeps alive after the layer that used them take $531$~MB, more than twice the
$204.5$~MB of weights that either mechanism removes.

FSDP cannot help here, and it does not. At $B{=}512$ the peak is $211.9$~MB on
one GPU and $214.9$~MB per rank at both $P{=}2$ and $P{=}4$. There are only

than that.

Equation~\ref{eq:bab-law} lets us estimate what splitting the subdomains would
give. If a global batch $B$ is spread over $P$ GPUs, each holds $B/P$
subdomains and needs $21.3 + 0.372\,B/P$~MB. For $B{=}512$ that is $45.0\%$
less memory per GPU at $P{=}2$ and $67.5\%$ less at $P{=}4$ ($49.3\%$ and
$73.9\%$ at $B{=}4096$). Each GPU then does exactly the work of a single-GPU
run at $B/P$, which Table~\ref{tab:bab-breakdown} measures directly. The
estimate leaves out the cost of gathering the per-rank results. Since $B$ is a
parameter, the same law can be read the other way. At a fixed memory budget per
GPU, $P$ GPUs bound $P$ times more subdomains in each round, and in practice
this throughput gain is probably the more useful one.

Our implementation of this split is unfinished. When the domains are scattered
before \texttt{build\_history\_and\_set\_bounds}, each rank builds its own state
and bounds its own chunk correctly. Domain parallelism and FSDP do not mix,
though. Once the ranks hold different subdomains, their sequences of per-layer
\texttt{AllGather} calls diverge and NCCL deadlocks, so we turn weight sharding
off in this mode. With $2.03$~MB of weights this costs nothing. The gather of
the per-rank results still stalls, which is why the numbers above are an
estimate.

\subsection{Convolutions and Transformers: Correctness Checks}
\label{sec:exp-arch}

The last set of runs checks that the sharding code works beyond MLPs. Memory
moves by at most 3\% in either direction here, so we read these runs as
correctness checks and nothing more. The first model is the VNN-COMP'23 ViT
\texttt{pgd\_2\_3\_16} \cite{arXiv2312VNNCOMP2023}, with 2 blocks, 3 heads and
$0.3$~MB of weights. After the three JIT fixes of Section~\ref{sec:fsdp},
FSDP=2 completes 78 BaB domains in 10 rounds at $1\,020.1$~MB per rank, and
$|\Delta lb| = 0.00$ at printed precision. As far as we know, this is the first
Transformer that has gone through BaB in $\alpha,\beta$-CROWN with sharded
weights. The other models are CIFAR-100 ResNets \cite{arXiv2412VNNCOMP2024}
with \texttt{BoundConv} sharding (batch 64, \texttt{max\_iterations} 5).
ResNet-med runs 130 domains in 5 rounds at $930$~MB per rank against $960$~MB
on one GPU and ends with \emph{unknown} when its budget runs out. ResNet-large,
with about $95$~MB of weights, is proved \emph{unsat} by $\alpha$-CROWN already
at initialization, at $4\,641.5$~MB per rank against $4\,610.6$~MB on one GPU.
No BaB ran in that case, and the FSDP peak is the higher of the two. The
\texttt{AllGather} buffers cost more than sharding $95$~MB of weights saves,
since the $\alpha$ tensors alone take over 4~GB.

\section{Related Work}
\label{sec:related}

\paragraph{Bound propagation.} CROWN \cite{CROWNPaper} introduced the backward
linear relaxation, $\alpha$-CROWN \cite{AlphaBetaCrownVNNCOMP23} and
$\beta$-CROWN \cite{betaCROWN2021} added optimizable slopes and dual encoding of
branching constraints, DeepPoly \cite{DeepPolyAbstractDomain} works in a
polyhedral abstract domain and OSIP \cite{arXiv2212OSIP} optimizes symbolic
interval propagation.

\paragraph{Parallel and multi-GPU verification.} Earlier parallel verifiers
follow two lines, and neither deals with the memory of the parameters. The
first splits the search space. Marabou's Split-and-Conquer
\cite{Wu2020Parallelization} splits the input domain across CPU workers
with iterative deepening, and $\beta$-CROWN \cite{betaCROWN2021} batches
subdomains on one GPU. The second moves a fixed abstract domain to the GPU, as
GPUPoly \cite{ScalingPolyhedralGPU} does for DeepPoly. Both scale the
\emph{number} of subproblems, while we looked at the memory of one. Our
measurements show that this memory sits in the subproblem batch, so splitting
domains and saving memory are the same problem.

\paragraph{Sharding for training.} Megatron-LM \cite{MegatronLM2020} introduced
intra-layer tensor parallelism, ZeRO \cite{ZeROPaper} shards parameters,
gradients and optimizer states, and GPipe \cite{GPipePaper} pipelines groups
of layers with micro-batches. As far as we know, none of them had been tried on
bound-propagation verification before. The negative result is worth recording
because the two workloads differ in a basic way. A training step is dominated
by parameters and optimizer state. A verification pass is dominated by tensors
indexed by specifications and subdomains.

\section{Conclusion}
\label{sec:conclusion}

Of the two methods, only TP reduced memory. It splits the $A$-matrices together
with the weights, so its memory and time scale almost linearly with the number
of GPUs. Its weak point is tightness, since only the first sharded zone keeps
exact bounds and the later zones use IBP. FSDP kept the bounds bit-identical,
but on our MLPs it raised peak memory, and copying the weights from host memory
did better. This is because in our MLPs the weights are only $6$--$11\%$ of the
peak. Sharding them can save a few percent at most, which is less than the
gathered copies cost.

For us the more useful result is the memory measurement itself. In incomplete
verification the $A$-matrices take $5.6$ times more memory than the weights at
$h{=}4096$. In complete verification the peak is $21.3 + 0.372\,B$~MB for $B$
subdomains, and weights are $0.13\%$ of it. Multi-GPU verification should
therefore split the subdomains. We estimate $45.0\%$ and $67.5\%$ less memory
per GPU at $P{=}2$ and $P{=}4$, or $P$ times more subdomains per round at the
same memory. In our code the scatter of subdomains already works on each rank,
and the gather of per-rank results is still missing. A harder open problem is
to shard the specification axis without the IBP fallback, so that the later
sharded zones also get exact intermediate bounds.
